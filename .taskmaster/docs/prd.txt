Unified User Management Solution Design
1. Use MongoDB as the Single Source of Truth for Users
All user data – including authentication credentials, roles, and status – should be centralized in MongoDB. This eliminates the split between Sanity and MongoDB for user accounts. In practice, this means creating and updating users in MongoDB first, and treating Sanity as a secondary store only for content-related references. Currently the code inserts new users into both databases[1][2]. Going forward, MongoDB will be the authoritative source for user records, and Sanity will no longer be manually maintained for user info.
•	Unified User Schema in MongoDB: Extend the MongoDB user model to include all necessary fields (name, email, hashed password, role, status flags like active/suspended, timestamps, etc.) that were previously split with Sanity. For example, the admin panel expects fields like role and status on users[3], so those should exist in the MongoDB schema. Ensure email remains unique in MongoDB (and Sanity) to serve as a reliable identifier for linking.
•	Unique Identifier for Linking: Use a unique field (email or a user ID) to map between MongoDB and Sanity users. The system already uses email to find or create the corresponding Sanity user[4]. Email is a practical choice as long as it remains immutable; otherwise, storing the Mongo _id in Sanity (and vice versa) could be a robust alternative. In either case, maintain a one-to-one correspondence between the Mongo user and any Sanity profile document.
2. Admin Panel – Centralized User Creation & Management
Introduce a complete User Management interface in the Admin Panel for super-admins to handle all user operations. This will be the single place to create new users, assign roles, and activate/suspend accounts, addressing the current gap where no in-app user creation exists. The admin panel already has a foundation for listing users and toggling status; we will extend this:
•	Create User Functionality: Add an “Add New User” workflow in the admin UI. This might be a form where a superAdmin can input name, email, password, and select a role for a new user. Submitting the form calls a Next.js API route (e.g. /api/admin/create-user) which will:
•	Create the user in MongoDB – Insert a new user document with the provided data. Assign a default role (or the selected role) and hash the password if using credentials. Using NextAuth’s Mongo adapter or a Mongoose model is fine (the project already has a registration route doing this)[5][6].
•	Create the user in Sanity – Immediately create a corresponding Sanity document for that user (for content linking). This Sanity profile can store the user’s name, email, and any profile info needed for listings or blog posts. Because we want Mongo as the single source, you can minimize fields in Sanity (just what's needed for references, like name/email/avatar). If the Sanity user schema was stripped of the role field during refactoring, you might reintroduce it or add a hidden metadata field to track role for reference logic – more on this below. The key is that this Sanity creation happens automatically via the API, not manually in Studio. This could reuse the existing createSanityUser utility. (In fact, the current registration logic already calls createSanityUser after saving to Mongo[6].)
•	Role Assignment & Changes: Allow superAdmins to change a user’s role from the admin panel (this was mentioned as a desired bonus). For example, a “Promote to …” action in the UI can call an API endpoint to update the user’s role. Internally, this will update the MongoDB user document’s role field. To keep Sanity in sync (if you keep the role there for any reason), also patch the Sanity document’s role field via the Sanity API. The admin UI design already anticipates a promote action[7], which we can implement to toggle roles (e.g. promote a normal user to editor or venueOwner). After a role change, if the user is currently logged in, you might force a re-fetch of their session or use NextAuth callbacks so the new role reflects in their JWT session token.
•	Activate/Deactivate (Suspension): The admin panel’s activate/suspend toggles should update a status field in MongoDB (e.g. active vs suspended). This can be a simple boolean or an enum field on the user. Once updated in Mongo, it can be respected by the auth logic (for example, the authenticateUser function can check user.status and disallow login if suspended). The UI already considers statuses like active, suspended, pending[8]. These status changes don’t necessarily need to reflect in Sanity (since content references to a user can remain even if the account is inactive), but you could include a flag in Sanity for completeness if needed.
Why this approach? By funneling all user management through a controlled admin interface (backed by MongoDB), we ensure there is no “second place” where users are manually created or modified (resolving issue #1). SuperAdmins can do everything – create accounts, assign roles, enable/disable users – without opening Sanity Studio. This reduces confusion and keeps the data consistent.
3. Synchronize Sanity for Content References
Even though MongoDB is the primary user store, we need to maintain the link to Sanity for content like listings and blog posts (to solve issue #3). The goal is to have a single source of truth (Mongo) while still leveraging Sanity’s reference fields for content. There are two possible strategies:
(a) Mirror Minimal User Profiles in Sanity: Continue using Sanity’s user documents for things like listing ownership and blog post authors, but auto-manage these docs. In this approach, whenever a user is created or updated in MongoDB, we propagate those changes to Sanity:
- On user creation (whether via admin panel or user self-registration), after writing to Mongo, create a new Sanity user document. Include fields needed by content: typically name, email, avatar image, and maybe a reference to their listings or posts (Sanity can maintain those via its relational schema). You can omit the role in Sanity or keep it only for internal CMS logic. For uniqueness, the email can serve as the key (the code already checks if a Sanity user with that email exists to avoid duplicates[4]).
- On user profile updates (if you allow editing names, avatars, etc.), update the Sanity doc via the API. For example, NextAuth’s signIn callback already updates the Sanity profile’s name/avatar on each login[9], ensuring the Sanity copy isn’t stale. A similar approach can be used if an admin edits a user’s info – just call updateSanityUserWithAuthDetails.
- On role changes: If you keep a role field in Sanity for any gating logic, update it here as well (e.g., via the updateUserRole helper or a new patch call). Otherwise, role can be omitted from Sanity if it’s not needed in content.
This one-way synchronization (Mongo ➡️ Sanity) means editors using Sanity Studio will always have up-to-date user references to attach to content, but they won’t create or edit users from Sanity. In fact, you could restrict the Sanity Studio permissions so that the user document type is not directly editable by content authors, to avoid out-of-sync changes. Sanity simply acts as a mirror of the user list for reference purposes.
(b) Reference Users by External ID (avoiding Sanity user docs): As an alternative, you could remove the need for a Sanity user document altogether by changing how content references owners/authors. For example, blog posts and listings could store a user’s MongoID or email in a plain field instead of a Sanity reference. However, this is less ideal with Sanity’s schema: you’d lose the nice reference picker UI and referential integrity. It also complicates queries (since GROQ queries would only have an id/email and would need a separate call to get user details from Mongo). Given the current tech stack, maintaining the Sanity user doc (strategy a) is simpler and provides a better editor experience. We just need to ensure those docs stay synced with the real user data.
In summary, the recommended approach is to keep Sanity for content relationships but automate its data. This satisfies the need for a single management source while still leveraging Sanity’s strengths for content. The NextAuth configuration is already partway there – e.g., it creates/updates Sanity users on sign-in[9] and on new user registration[10]. We will build on that to cover all user lifecycle events (create, update, role change, etc.) in a consistent way.
4. Handling Listings and Blog Post Authors
With the above sync in place, listings and blog posts can continue referencing users seamlessly. Sanity’s schema currently likely has blog posts referencing an author of type user, and users referencing owned listings. Here’s how the new setup affects these:
•	Blog Post Authors: Blog posts will still have an author field that is a reference to a Sanity user document (one-to-one relationship)[11]. Editors can pick an author from the list of users. Because we now ensure all actual users exist in Sanity (via sync), the list will include anyone who can be an author. We should clarify how non-admin editors get into that list: e.g., if a normal user registers on the site, a Sanity profile is created for them too – which is fine if they might write a blog or be referenced. If not, you could filter which users appear (perhaps based on role or a flag). But from a system design view, it’s simplest to include all users as potential authors and use role-based gating in the app (for instance, only allow those with an “editor” role to access blog writing features on the site). The key is that Sanity remains the source of blog content, but it no longer owns the truth about the user’s identity beyond storing a reference. If a user’s name or avatar changes, the sync will update the Sanity document so the blog author info stays current.
•	Listing Owners: Currently, the schema indicates a user document holds an array of ownedListings references[12], and by a business rule only users with role “venueOwner” or “admin” should have owned listings[13]. To maintain this with a single source of truth:
•	We should reintroduce or retain the role field on the Sanity user doc, or otherwise indicate in Sanity which users are allowed owners. The simplest path is to keep the role on Sanity (synchronized with Mongo’s role). This way, the existing Sanity logic (hidden: ({ document }) => document?.role !== 'venueOwner' && ... in the schema) will continue to hide or show the Owned Listings field appropriately. If the role field was removed, consider adding it back just for this conditional UI benefit – it can be auto-set via sync whenever a user’s role changes.
•	Assigning owners: An admin can assign a listing to an owner either by editing the user’s ownedListings field in Sanity Studio or via a custom tool. To streamline, you might implement this in the admin panel too: e.g. on the listing edit page in the app, allow selecting an owner (which under the hood would patch the Sanity user’s ownedListings array for that owner user). This avoids having to go into Sanity Studio to attach owners. Regardless of where it’s done, because all users and their roles are present in Sanity, the relationship can be managed.
•	If a user’s role is changed to or from venueOwner, you’ll want to handle their listings accordingly. For example, if someone is demoted from venueOwner to regular user, their existing ownedListings could remain but violate the rule. Business-logic-wise, you might enforce that only venueOwner/Admin can actually create or be assigned new listings. The system can periodically check or enforce that rule (since it’s documented as a constraint). Keeping the roles synced in Sanity makes it straightforward to uphold this in the CMS interface.
In both cases, Sanity remains the source for the content pieces (listings, blogs), but it depends on an updated list of users for references. By syncing on each user change, we satisfy that need. The end result is content objects still reference a Sanity user document (no schema change needed for BlogPost or Listing), but those user documents are created/updated by our application logic, not by editors manually.
5. Authentication Flow with Auth.js (NextAuth)
Continue using NextAuth (Auth.js) with the MongoDB adapter for authentication, but align it with the new unified user store:
•	NextAuth Adapter & User Model: Ensure the NextAuth Mongo adapter is aware of the custom fields like role and status. In NextAuth v5, the Mongo adapter will store users in a users collection. You may need to extend it so that when a new OAuth user signs up, a default role (user) is saved. In the current setup, the code adds role: 'user' in the profile callback for Google/GitHub[14][15] and includes role in the JWT/session[16][17]. However, that role might not have been persisted in the database for OAuth users. As part of the solution, use the NextAuth events.createUser callback or a custom adapter to insert a default role into the MongoDB user record when an OAuth account is created. (The code skeleton already notes this in the createUser event, defaulting role to 'user'[18].) This way, all MongoDB user entries have a role field, whether they came from credentials or OAuth.
•	Login and Sync: When a user logs in (credentials or OAuth), NextAuth’s callbacks will continue syncing their Sanity profile. The existing signIn callback already checks for a Sanity user and creates one if missing[9]. We should keep that in place (or move it to the createUser event as needed) so even if a user registers externally (e.g., OAuth sign-up bypassed our admin flow), we catch it and create the Sanity doc. Essentially, any path of user creation (admin-created, self-register, or OAuth) triggers the creation of the Sanity profile. This covers all bases.
•	Authorization (Role-Based Access): With roles unified in Mongo, protecting admin routes becomes straightforward. Use NextAuth’s session (which now carries session.user.role) to guard pages – e.g., only admin role can access the user management page, only editor can access blog post writing pages, etc. Since the session includes the role[17], this is simply a matter of checking session.user.role in Next.js route handling or using middleware. There’s no more need to check Sanity for role when determining access. This centralizes auth logic to one place.
6. Avoiding Conflicts and Maintaining Consistency
With the above design, a few additional considerations ensure smooth operation:
•	Disable Direct Sanity User Edits: If possible, configure Sanity Studio to prevent creating or editing user documents manually (except perhaps by an admin developer). This could be done by adjusting roles/permissions in Sanity or by not exposing the user schema in the studio for content editors. The aim is to avoid a scenario where someone adds a user in Sanity that doesn’t exist in MongoDB – since that user couldn’t log in and would cause confusion. All user additions should come through the app’s workflow.
•	Email Uniqueness: Continue to enforce unique emails across both systems. The Sanity schema marks email with unique (or at least isUnique) and the code checks for an existing Sanity user before creating[19]. Keep these checks so we don’t end up with duplicate profiles. The admin create-user API or registration route already handles this by checking Mongo then Sanity[20][19]. This ensures a one-to-one mapping between a Mongo user and a Sanity profile.
•	Data Migration: Since roles were removed from Sanity in a previous refactor, you may need to migrate existing Sanity user docs to reintroduce the role field (if you choose to use it for OwnedListings logic). You can script a one-time update: for each user doc in Sanity, find the corresponding Mongo user by email and set the Sanity role field accordingly (e.g., via Sanity API or a CLI script). This will realign Sanity with the current roles from Mongo. After this, the ongoing sync will keep them updated.
•	Consistency Audits: It might be wise to periodically verify that every Mongo user has a corresponding Sanity doc (and possibly vice-versa), especially if there were multiple creation paths historically. Running a small script or a backend check that compares the two lists by email and creates any missing ones can catch any outliers from before this unified approach.
By implementing the above solution, you achieve a clean separation of concerns: MongoDB becomes the sole authority for user accounts and authentication, and Sanity is used only for content and content-related pointers to users. The admin panel becomes the one-stop interface for user management (solving the creation and role-management issues), and behind the scenes the system keeps the two databases in sync where necessary. This design adheres to best practices by avoiding duplicate manual work and ensuring data consistency, while still making the best use of each component of your tech stack. The result will be a more maintainable system where all aspects of user management are handled in one place, as requested, with no loss of functionality in the CMS content relationships.
