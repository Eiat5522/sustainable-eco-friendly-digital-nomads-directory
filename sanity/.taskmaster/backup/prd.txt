# Admin Dashboards — Product Requirements Document (PRD)

Overview

The Admin Dashboards provide site administrators and authorized moderators with a single place to monitor community health, manage content and users, run bulk operations, and perform moderation workflows for the Sustainable Eco-Friendly Digital Nomads Directory. The admin experience enables safe, auditable interventions, fast triage of flagged content, insight into usage and growth, and tools to maintain quality and sustainability standards.

Core features

1) Admin Landing / Dashboard
- What it does: Presents KPIs and an at-a-glance view of system health: total users, total listings, total reviews, weekly signups, pending moderation tasks, and role distribution.
- Why it's important: Gives admins quick situational awareness and points of action for moderation and content curation.
- How it works: Server-rendered dashboard (Next.js app route) fetches analytics from `/api/admin/analytics`. Dashboard includes overview cards, last refresh time, and links to moderation, content analysis, and bulk operations.

2) Moderation Queue & Tools
- What it does: Lists flagged items (listings, reviews, comments, events, etc.) that require review with context, reporter reasons, and actions (Notes, Approve, Restrict, Escalate).
- Why it's important: Ensures community standards are enforced, reduces false positives, and centralizes moderation.
- How it works: `GET /api/admin/analytics` (or a dedicated `GET /api/admin/moderation`) returns moderation items. Moderation actions call App Routes (`POST /api/admin/moderation`) which update Sanity documents or moderation status records. Actions are logged with the admin ID and timestamp for audit.

3) Content Analysis & Auto-scan
- What it does: Allows admins to run content analysis (e.g., profanity, sustainability-tag checks, spam detection) or view automated scan results and flagged items.
- Why it's important: Automates initial triage, surfaces policy violations, and supports bulk review.
- How it works: `POST /api/admin/analyze-content` triggers server-side jobs (sync or background) which return a scan result summary and suggested actions. For heavier jobs consider async queueing (webhooks, job queue, or serverless background runs).

4) Bulk Operations & CSV Import/Export
- What it does: Perform bulk updates (e.g., change listing status, add/remove sustainability tags), import CSVs for mass updates, and export moderation/analytics data.
- Why it's important: Speeds administrative workflows and allows dataset corrections without per-item edits.
- How it works: UI endpoints use `POST /api/admin/bulk-operations` for server-validated operations. Imports should be validated first on server side. Provide preview/dry-run mode and detailed operation logs.

5) Role & Access Management (RBAC)
- What it does: Define admin, moderator, contentEditor, venueOwner, and other roles; manage user access to admin functionality.
- Why it's important: Security and auditability; prevents privilege escalation.
- How it works: Roles are canonicalized in Sanity. Server routes call `auth()` to verify sessions and check `session.user.role === 'admin'` or other allowed roles. Implement server-side checks for every admin route. Provide UI to invite/assign roles (Sanity Studio or admin UI) with two-factor or email confirmation workflows for sensitive role changes.

6) Audit Logs & Change History
- What it does: Record actions performed by admins (approve/restrict/bulk ops), who performed them, and when.
- Why it's important: Accountability, rollbacks, and legal/compliance support.
- How it works: Create an `adminAction` Sanity document (or a dedicated logging DB) capturing action type, target id/type, admin id, timestamp, and a free-text note. Provide filterable audit views and export options.

7) Health & Alerts
- What it does: Surface system alerts (errors in background jobs, high moderation backlog, unusual activity spikes) and allow subscription to alert channels.
- Why it's important: Early warning and SLA management.
- How it works: Integrate with monitoring (Sentry, Datadog) and internal heuristics. Provide threshold-based alerting and Slack/email webhook configuration.

User Experience

User personas
- Admin: Full access to view analytics, run scans, perform moderation, and run bulk ops.
- Moderator: Limited to moderation queue and approve/restrict actions, plus note-taking.
- Content Editor: Can edit and approve content but not change roles or perform destructive bulk ops.
- Venue Owner: Can manage own listings and respond to moderation on owned content.

Key user flows
- Admin login -> Dashboard -> Click moderation task -> Review details -> Approve/Restrict -> Action logged and UI updated.
- Admin -> Bulk operations -> Upload CSV -> Preview -> Run dry-run -> Confirm -> Execute -> View logs.
- Admin -> Run content analysis -> View flagged items -> Send to moderation queue.

UI/UX considerations
- Keep the dashboard primarily server-rendered for performance and SEO (Next.js app router server components) while enabling interactivity via client components for actions.
- Provide clear success/failure states and optimistic updates for moderation actions, with server-driven confirmation and fallback.
- Accessibility: Ensure keyboard navigation, screen reader labels, and color contrast for status badges.

Technical Architecture

System components
- Frontend: Next.js (App Router) TypeScript + TailwindCSS. Server components for initial dashboard render, client components for interactive moderation actions.
- Backend: Sanity CMS as the primary content store; Node/Next App Routes as API layer. Optional small service or job-worker for long-running content analysis tasks (e.g., serverless functions or queue consumer).
- Auth: NextAuth.js (v5) using provider(s) configured for production (OAuth, email, or SSO). Sessions must include canonical `role` on the user object.
- Logging & Monitoring: Sentry/Datadog for error tracking; optional Prometheus metrics for backlog counts.

Data models
- Sanity documents (existing): `user`, `listing`, `review`, `moderationStatus`.
- New/extended documents:
  - `moderationStatus` (type): { status: 'pending'|'approved'|'rejected'|'flagged', item -> reference, reports: array, lastActivity, assignedTo? }
  - `adminAction` (type): { admin->reference, actionType, targetId, targetType, note, timestamp, metadata }

APIs and integrations
- GET /api/admin/analytics — returns overview counts, role distribution, moderation queue (secured, server-side RBAC)
- POST /api/admin/moderation — apply moderation action (approve/restrict/note) with validation and audit logging
- POST /api/admin/analyze-content — triggers content analysis job (sync lightweight or async with job id)
- POST /api/admin/bulk-operations — server-side validated bulk changes with dry-run mode
- Optional admin endpoints for CSV import status & audit logs

Infrastructure requirements
- Ensure Sanity has adequate read/write capacity and consider using a separate, indexed collection for audit logs if high volume is expected.
- Job queue (Redis/BullMQ, or serverless queued functions) for heavy content analysis.
- Secrets management for NextAuth and Sanity API tokens; ensure test and prod tokens are separated.

Development Roadmap

MVP (must-haves to ship a usable admin dashboard)
- Server-rendered Admin Dashboard with metrics from `GET /api/admin/analytics` and basic moderation table displaying last 10 items.
- Server-side RBAC enforcement on admin routes using `auth()` and role checks.
- `POST /api/admin/moderation` to perform approve/restrict actions and create `adminAction` audit entries.
- Simple client components to trigger moderation actions and update UI on success/failure.
- Unit tests for route handlers and auth checks; a small E2E test that logs in as admin and navigates to dashboard.

Phase 2 (immediate improvements)
- Bulk operations endpoint & UI with CSV import & dry-run.
- Content analysis endpoint & lightweight background job runner.
- Pagination for moderation queue and filters by item-type/status/date.
- Audit log UI and export.

Phase 3 (scale & polish)
- Asynchronous large-job processing with persistence, retries, and progress tracking.
- Role management UI (invite/assign roles), 2FA for sensitive role modifications.
- Alerts & integrations (Sentry, Slack webhooks).

Logical dependency chain
- Foundation: Auth and RBAC (NextAuth + `auth()` utility), Sanity schema changes for audit logging/moderation statuses.
- Middle: Admin analytics route + dashboard UI (server side) to present data.
- Next: Moderation action endpoints and client wiring (approve/restrict/actions) plus audit logging.
- Then: Bulk operations & content analysis features.
- Final: Scaling features (job queue, alerts) and admin role management UX.

Risks and mitigations
- Risk: Sensitive admin actions run without audit logging or proper RBAC — Mitigation: enforce server-side auth checks and write an `adminAction` document on every action before commit; add tests.
- Risk: Heavy content-analysis jobs block the server — Mitigation: offload to background workers or serverless jobs; provide async job endpoints and progress tracking.
- Risk: Role inconsistency between Sanity schema and API queries — Mitigation: standardize role enum, validate role values on read/write, and add a migration script if necessary.
- Risk: E2E tests failing due to environment variables or NextAuth client issues — Mitigation: add local dev/test env docs, a script to generate test JWTs (exists), and mock-next-auth strategies for unit tests.

Appendix
- Research notes: Use Sanity GROQ queries for moderation slices; for heavy aggregates prefer indexed collections or a secondary analytics store.
- Implementation notes: Prefer server-side fetch for analytics and client components for interactive moderation actions; ensure `NEXTAUTH_URL` and NextAuth session cookies are available to server/runtime.
